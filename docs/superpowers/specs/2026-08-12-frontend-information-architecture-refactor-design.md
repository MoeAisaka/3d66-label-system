# LabelLab 前端信息架构与评测机制编辑器重构设计

- 日期：2026-08-12
- 状态：Owner 已确认
- 实施基线：Codeup `main@ca829b72c212ae7aa68a9d5c4add75fbd01966d6`
- 目标分支：`codex/frontend-information-architecture-v1`
- 测试环境：`http://192.168.1.35:8081`

## 1. 背景与问题

TPENG 标签实验台已经是标签体系重构的统一产品载体，也是标签/内容中台重构的通用底座。随着模型注册、类目机制、人工纠偏、AI 迭代、发布、回归与治理能力持续增加，当前前端暴露出四类结构性问题：

1. 高级设置域在页面顶部重复展示“高级设置首页 / 类目评测底座预览 / v3 合同配置”三个入口；进入任意高级设置页面后，现有激活判断还会让三个入口同时呈现选中状态。
2. v3 合同页假设 `track_classification.tracks` 永远是数组。`proposal_text_pdf` 的 `text-proposal-additive-v1` 合同使用对象型赛道，并且 `classification_map`、`subcategory_dimensions` 也不是通用图像结构，当前页面调用 `tracks.map` 后直接白屏。
3. v3 图像规则合同只有 `deduction_rules`，缺少 `bonus_rules` 与显式维度分数上限；操作员无法表达正向规则，也无法明确控制维度内部封顶。
4. 大量页面把创建表单、运行参数、历史、指标、诊断、证据和主操作同时平铺。存量回归页尤其明显：逐条确认与纠偏作为主任务只得到很小区域，创建基准集、运行配置、混淆矩阵和历史轮次反而长期占据一级页面。

本设计采用“统一页面框架 + 渐进式重构 + 机制插件注册”。本批完成高级设置、v3 合同配置和存量回归三个高优先级页面，并产出其余页面的信息架构审计；不一次性重写全部前端。

## 2. 目标

### 2.1 产品目标

- 一级页面只保留完成当前主线所需的状态、最低必要输入和主要操作。
- 配置详情、历史证据、低频参数和诊断信息使用一致的二级承载方式。
- 评测机制按合同类型扩展，同一类目可以选择不同机制，3D、SU 等后续专用机制不复制平台外壳。
- 所有未知或损坏机制都必须安全降级，不允许再出现整页白屏。
- 新增加分与维度封顶能力时，旧合同、旧结果和冻结回放保持可解释、可复现。
- 前端明确展示产品版本与构建提交，便于测试环境对账和回退。

### 2.2 工程目标

- 把目前超大页面中的通用页面结构、抽屉、Dialog、错误边界和版本展示拆成可复用单元。
- 保持现有 API、权限、双发布轴、人工发布门禁和测试环境部署流程不变。
- 按小步提交实施，每一步均可独立构建、测试和回退。

## 3. 非目标

- 本批不实现 3D、SU 专用机制编辑器，只建立注册和降级能力。
- 本批不重构其余约 20 个页面，只输出逐路由审计与后续批次清单。
- 不支持或验收移动端。系统限定为公司内网有线网络下的桌面浏览器工具。
- 不修改生产环境，不执行存量数据批量重跑，不覆盖正式标签事实。
- 不改变机制发布轴与标签事实发布轴的独立关系。
- 不把 `proposal_text_pdf` 转换为图像类目的维度扣分合同。
- 不增加任意代码插件；机制注册仍是服务端和前端代码中受控、可审计的注册表。

## 4. 设计基线

### 4.1 桌面与视觉

- 主设计基准：`1440×900`。
- 最低验收尺寸：`1280×720`。
- 更宽屏幕自适应，内容区域设合理最大宽度并优先扩展主操作区。
- 不新增移动端导航、断点或验收用例；现有窄屏兼容可以保留，但不作为本批完成条件。
- 品牌色固定为 `#CCED46`，仅用于主操作、当前选择、进度和键盘焦点，单屏占比保持克制。
- 使用白色/浅灰工作区、深色文字、淡分割线和微软雅黑；禁止霓虹光晕、暗色模式、普通面板重阴影、紫蓝渐变和卡片堆叠。
- 状态不能只靠颜色表达，必须同时包含文字或图标。

### 4.2 信息分层

| 内容类型 | 承载方式 | 适用内容 |
|---|---|---|
| 持续影响当前决策的信息 | 一级页面 | 当前对象、状态、进度、阻塞、主要输入、主要操作 |
| 需要边看主页面边修改的复杂内容 | 右侧宽抽屉 | 运行参数、配置详情、版本差异、指标、证据、历史 |
| 短表单或不可逆前确认 | Dialog | 新建基准集、删除/取消确认、短参数提交 |
| 少量补充上下文 | 行内展开 | 简短说明、次要字段、单条错误详情 |
| 需要连续编辑、对比或逐条操作的任务 | 独立工作台模式 | 合同编辑、逐条纠偏、长时间人工验收 |

宽抽屉使用现有 Radix Dialog 基础能力实现，提供焦点锁、Esc 关闭、标题描述、关闭按钮和返回焦点；普通静态面板不使用阴影，只有浮层使用设计系统定义的 floating shadow。

## 5. 通用前端架构

### 5.1 应用壳

`AppShell` 保留现有主工作域导航，但作以下调整：

- 高级设置域不再渲染顶部二级快捷导航；开始评测、处理纠偏等有顺序含义的主工作域可以继续保留其步骤导航。
- “类目评测底座预览”和“类目评测 v3 合同配置”下放到高级设置页“评测方案”常规入口组。
- 高级设置本身通过左侧主导航进入，不在页面内增加指向自己的重复入口。
- 侧栏用户区上方展示：`LabelLab v0.2.0 · build <7位Git短SHA>`。
- 产品展示名称统一使用 `LabelLab` / `TPENG 标签实验台`，不改变现有 API、仓库名或历史审计标识。

版本实现采用单一模块读取：

- 产品版本来自 `frontend/package.json`，本批提升为 `0.2.0`。
- 构建 SHA 在 Vite/Docker/部署构建时由 Git 注入。
- 本地开发无法取得 SHA 时显示 `build dev`，测试环境不得使用该回退值。
- 部署验收必须同时核对页面构建 SHA、服务器部署 SHA 和 Codeup 合并提交。

### 5.2 共享页面组件

本批建立以下边界清晰的通用组件，名称可以按现有代码风格微调，但职责不得混合：

- `WorkspacePageHeader`：标题、简述、上下文状态和一级操作。
- `StatusSummaryStrip`：少量持续可见的关键状态，不承载大段说明。
- `SecondaryDrawer`：复杂配置、详情、历史、指标和证据。
- `ConfirmDialog`：短表单与确认操作。
- `InlineDisclosure`：少量次要信息的行内展开。
- `RouteErrorState`：路由或查询失败时显示可恢复错误，不渲染空白页面。
- `MechanismEditorBoundary`：捕获机制编辑器渲染异常，显示合同身份、错误摘要、重试和只读 JSON 入口。
- `AppVersion`：格式化产品版本和构建 SHA。

通用组件只定义布局、可访问性和交互，不包含具体业务字段或类目判断。

## 6. 高级设置页

### 6.1 一级页面保留

- 权限状态和需要管理员立即处理的阻塞。
- 按领域分组的常规入口清单。
- 每个入口的名称、用途、当前可用状态和主要跳转动作。

“评测方案”组至少包含：

- 类目评测底座预览。
- 类目评测 v3 合同配置。
- 提示词版本。
- 模型注册中心。

### 6.2 二级承载

- 入口的完整能力说明、依赖关系和低频提示进入抽屉或目标专页。
- 审计与历史不在高级设置首页重复平铺。
- 不再渲染高级设置顶部三个快捷入口，因此也不再保留“三项同时选中”的错误路径。

## 7. V3 机制插件架构

### 7.1 注册原则

编辑器按“解析后的机制类型”路由，而不是按类目名称写 `if category_key`：

```text
合同详情
  → resolve mechanism profile
  → 查找受控 plugin registry
  → 加载 editor + validator + summary
  → 未注册或解析失败时进入只读安全降级
```

注册项至少包含：

```ts
type MechanismEditorPlugin = {
  profileType: string
  canEdit: boolean
  Editor: React.ComponentType<MechanismEditorProps>
  buildSummary: (detail: ConfigDetail) => MechanismSummary
}
```

服务端维护对应的受控校验注册表。前端是否显示编辑器不能替代服务端校验。

### 7.2 机制类型解析与兼容

- 显式存在 `contract.profile_type` 时，以该值为唯一机制类型。
- `text-proposal-additive-v1` 注册为 Proposal PDF 专用插件。
- 现有标准图像 v3 合同历史上没有 `profile_type`。兼容解析器只对已知的
  `schema_version=evaluation-category-profile-v3` 且满足标准结构的合同映射为内建
  `image-rule-deduction-v1`；此映射不改写历史合同或冻结快照。
- 新建或另存的机制合同应显式持久化 `profile_type`，逐步消除隐式兼容。
- 未知 `profile_type`、无法确认的旧结构或损坏合同不得猜测类型，只能进入安全降级。

### 7.3 安全降级

未知或损坏机制页面仍展示：

- 类目、display name、revision、contract hash、profile type 或无法识别原因。
- 只读合同摘要与完整 JSON 查看/复制入口。
- “当前版本不支持结构化编辑”的明确提示。
- 返回列表、重新加载和查看校验错误的操作。

降级状态不调用任何通用数组方法，不自动转换对象，不保存合同，不允许白屏。

## 8. Proposal PDF 专用编辑器

`text-proposal-additive-v1` 保留原始合同对象并采用“左侧步骤导航 + 中央主编辑区 + 右侧校验/变更摘要”的桌面工作台。编辑器始终从完整合同深拷贝后做路径级 patch，保存时提交完整对象；禁止通过重新拼装已知字段丢弃未知或扩展字段。

### 8.1 编辑步骤

1. 合同身份：`spec_version`、A/B 版本、来源标准和显示名。
2. PDF 输入与确定性预检：文本层、OCR、调用 A 批次、调用 B 代表页和审计开关。
3. 红线与人工复核：红线规则、20 分封顶、终止语义和人工复核 fail-closed。
4. 赛道与三分项评分：A/B/C/balanced 对象型赛道、members、`visual_max`、`narrative_max`、`innovation_max`。
5. 等级与输出字段：L1-L5 区间、固定输出字段来源和基础美感分只读语义。
6. 回归与验收：主指标、每档召回门槛、已知风险和回归说明。

低频说明、完整 JSON、版本差异和审计字段使用抽屉；影响合同运行的核心参数不得只存在于隐藏 JSON 中。

### 8.2 原生评分语义

Proposal PDF 继续使用：

```text
score = visual_score + narrative_score + innovation_timeliness_score
```

每个分项受当前赛道对象中的对应上限约束，最终分数不超过 100。它不使用图像机制的 `deduction_rules`、`bonus_rules` 或 `dimension_score_cap`；后续其他加法机制通过新的 `profile_type` 插件扩展。

### 8.3 服务端校验

- `text-proposal-additive-v1` 保存和 dry-run 校验调用 `validate_proposal_text_contract` 及其专用 classification/dimensions 校验。
- 标准图像插件继续调用现有 v3 合同、分类映射和子类目维度校验器。
- API 根据解析后的机制类型路由校验，不再无条件把所有合同送入标准图像校验器。
- 未注册机制的写请求返回稳定错误码 `profile_type_unsupported`，读取仍可用。

## 9. 图像规则机制的加分与维度上限

### 9.1 合同字段

`image-rule-deduction-v1` 的每个维度增加：

```json
{
  "dimension_score_cap": 100,
  "deduction_rules": [],
  "bonus_rules": []
}
```

- `dimension_score_cap`：维度内部 0–100 分制的上限，必须是 `0..100` 的有限数值。新保存的候选合同必须显式写入。
- `bonus_rules`：可为空数组；每项包含 `rule_id`、`description`、`bonus`、`tags`。
- `bonus` 必须为大于 0 且不超过 100 的有限数值。
- 同一维度内扣分规则与加分规则的 `rule_id` 合并后必须唯一，避免证据和纠偏引用歧义。
- 新保存的规则型维度必须同时显式写出 `deduction_rules` 与 `bonus_rules`；两者允许任一为空，但至少一组非空，因此支持“仅扣分”“仅加分”和“扣加并存”。同一赛道仍禁止规则型维度与旧 `grade_points` 维度混用。
- 规则模式由原始合同中存在 `deduction_rules` 或 `bonus_rules` 字段识别。两个字段都不存在时才按既有 `grade_points` 兼容路径执行；不得仅因读取层补默认值就把旧合同切换到新规则模式。

旧合同缺少 `dimension_score_cap` 时在编辑/摘要层读取为 100，缺少 `bonus_rules` 时读取为空数组；这些兼容默认不写回原合同，不得批量改写数据库或冻结快照。

### 9.2 计分顺序

现有规则机制是“维度满分扣分制”。新能力在该机制内定义为：

```text
raw_dimension_score = 100 - Σ命中扣分 + Σ命中加分
dimension_score = clamp(raw_dimension_score, 0, dimension_score_cap)
dimension_contribution = frozen_weight_share × dimension_score / 100
```

- 加分可以抵消扣分或恢复维度表现，但不能让无扣分维度突破其上限。
- `dimension_score_cap=100` 时与现有维度满分行为一致。
- 前端同时展示内部上限百分制和按当前冻结权重换算的最大赛道贡献，避免把二者混淆。
- 各维度贡献汇总后继续应用现有媒介修正、硬伤策略、`track_cap` 和最终 `0..100` 限制。
- 若未来需要“从 0 开始累计正向分”的机制，应新增 profile plugin，不改变本机制的历史数学。

### 9.3 调用 B 与证据

新版规则调用 B 仍不输出总分或等级，只判断规则命中：

```json
{
  "dimensions": {
    "dimension_key": {
      "hit_rules": [],
      "hit_bonus_rules": []
    }
  }
}
```

两类命中均包含 `rule_id`、`confidence` 和独立中文证据。服务端验证 ID、重复命中和维度完整性后确定性计分。供应商失败延续现有主观评分节点的 fail-open 计分策略：扣分和加分命中均为空并记录 warning，不把整条评测改成无分结果；该 warning 同时标记为需要人工复核。合同损坏仍在调用前 fail-closed。这样既不因供应商瞬时故障伪造负向命中，也不会静默放过失败样本。

结果证据至少记录：

- 原始/应用扣分合计。
- 原始/应用加分合计。
- 上限前分数、上限后分数。
- 权重模式、有效 share 和最终赛道点数贡献。
- 命中的扣分/加分规则及证据。
- 触发维度上限、赛道上限或硬伤封顶的原因。

### 9.4 版本与回放

- 显式含 `dimension_score_cap` 或 `bonus_rules` 的新规则合同使用新的 composition/bridge 版本标识；原始冻结合同不含新字段时继续路由到既有 deduction composition，保证旧输出的版本、steps 和 evidence 形状不变。
- 运行和节点纠偏始终读取结果中冻结的完整 v3 context，不读取当前活动配置替换历史合同。
- 旧 fixture 和历史回放的结果、steps、cap reasons 不得因默认字段引入而变化。
- 首次保存由旧合同编辑出的候选时，编辑器显式写入默认 `dimension_score_cap=100` 与 `bonus_rules=[]`，形成新的 config revision/候选机制版本并切换到新 composition；不会改写旧 revision，也不会自动发布机制、重跑存量或写正式标签事实。
- `dimension_deduction_rules_json` 继续作为历史扣分镜像；`subcategory_dimensions_json` 是加分与上限的权威配置。除非后续另行冻结统一规则镜像，不为本批新增重复数据库列。

### 9.5 人工纠偏

节点纠偏编辑器在新合同下可以修改扣分命中与加分命中，并用同一冻结合同重算后续节点。旧合同只显示扣分命中，不伪造加分字段。纠偏事件继续只追加，不覆盖模型原始输出。

## 10. V3 合同页信息架构

### 10.1 一级保留

- 类目列表或紧凑选择栏。
- 机制类型、合同 revision/hash、草稿/启用状态和校验状态。
- 当前编辑步骤的核心字段。
- 校验、保存和创建候选版本动作。
- 实时错误摘要，错误必须定位到具体区块或字段。

### 10.2 二级承载

- 完整 JSON、版本差异、历史 revision 和审计证据进入宽抽屉。
- 低频输入通道细节可以在对应步骤内折叠，但不能从结构化编辑器消失。
- 未知机制只读摘要使用同一外壳，不加载任何不匹配的编辑组件。

## 11. 存量回归页

### 11.1 主操作链

一级页面围绕以下顺序组织：

```text
选择基准集 → 选择/查看回归轮次 → 逐条确认与纠偏 → 完成人工验收
```

持续可见的信息仅包括：

- 当前类目、基准集、轮次和机制/模型版本对比。
- 运行状态、总量、待确认数、偏差数和人工验收进度。
- 筛选、批量选择、上一条/下一条等高频操作。
- 逐条素材、冻结真值、候选结果、差异状态和确认/纠偏动作。

逐条操作区占据页面最大面积。在 `1440×900` 和 `1280×720` 下都不能被指标、历史或创建表单压缩成次要区域。

### 11.2 二级交互

- 新建/管理基准集：Dialog。
- 上传、素材包选择和大批素材挑选：专用 Dialog 或抽屉，提交后返回主线。
- 新回归的模型、提示词、合同和运行参数：宽抽屉。
- 指标、分档召回、混淆矩阵和解释：宽抽屉。

### 11.3 纠偏工作台

## 13. 错误处理

- 路由查询失败：保留应用壳，显示错误摘要、重试和返回入口。
- 机制解析失败：显示安全降级摘要，不尝试渲染通用编辑器。
- 插件渲染异常：`MechanismEditorBoundary` 捕获并显示错误状态，控制台保留诊断，但用户页面不为空。
- 合同校验失败：显示稳定错误码、目标路径和中文信息；禁止部分保存。
- 乐观锁冲突：提示配置已变化，要求重新加载并查看差异，不覆盖他人 revision。
- 未保存离开：编辑器显示明确的未保存状态并拦截误操作。
- 版本注入缺失：本地显示 `build dev`；测试部署门禁失败，不允许以未知构建号验收。
