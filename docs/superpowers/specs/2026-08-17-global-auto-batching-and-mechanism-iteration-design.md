# 标签实验台全类目自动组批与评测机制迭代设计

> 日期：2026-08-17  
> 状态：设计已由 Owner 确认，等待书面规格复核  
> 设计基线：`origin/main@50e5b1572dd3ea5b65a7641ca50ae32fd850df07`  
> 当前阶段：只提交设计文档，不实施业务代码、不推送、不部署、不启动真实任务

## 一、目标

补齐 TPENG 标签实验台从“人工纠偏”到“人工决定是否采用新机制”之间的自动闭环，并同时推进灵感图评测机制优化：

1. 所有正在纠偏的类目均可自动组批，不做灵感图单类目试点。
2. 人工完成最终纠偏后，系统自动完成案例校验、归因聚类、机制路由、候选生成、配对回归和证据汇总。
3. 人工在纠偏与候选二审之间不再配置策略或点击启动。
4. 人工仍负责最终采用或拒绝候选；系统不得自动启用机制、覆盖存量结果或发布标签事实。
5. 灵感图候选重点解决推荐档与常规档边界、第三档与第四档区分、第五档过滤召回。
6. 全部实现必须兼容标签实验台会话中尚未推送、合并和部署的迭代包。

## 二、已冻结的产品决定

### 2.1 全类目开放，严格隔离

- 所有存在人工纠偏输入的活动类目均建立自动优化泳道。
- 禁止跨类目混批、共享黄金集、共享候选或共享回归结论。
- 增量评测与存量回归共享执行内核，但任务上下文、案例池、候选和回归证据分开。
- 组批身份至少包含：
  - 类目标识；
  - 增量或存量链路；
  - 冻结机制指纹；
  - 纠偏节点路由；
  - 启用代次。

### 2.2 历史积压隔离

- 全局自动化启用前已存在的约 2,286 条历史待处理案例统一进入“历史审计队列”。
- 历史案例不会因为打开总开关而自动变成可消费案例。
- 只有人工明确复核并执行“纳入当前泳道”动作后，历史案例才能生成新的可消费副本；原始记录保持不变。
- 自动消费者只读取启用时间之后、匹配类目、链路和冻结机制版本的新纠偏案例。

### 2.3 零人工中间操作

人工完成最终纠偏后，系统自动推进以下步骤：

```text
最终人工纠偏
→ 完整性校验
→ 写入类目独立案例池
→ 自动组批与归因聚类
→ 判断修改调用甲、调用乙或第三版规则
→ 生成不可变候选机制包
→ 创建并跑完配对回归
→ 汇总质量、风险和失败样本
→ 进入人工候选二审
```

以下动作不得要求运营逐批点击：检查队列、选择优化模型、启动分析、创建候选、创建回归、刷新回归状态。

### 2.4 双人工门保持不变

- 第一道人工作业：运营纠偏并形成最终人工结论。
- 第二道人工作业：有权限的人员采用或拒绝候选机制。
- 候选采用只改变后续任务使用的现役机制，不自动重跑存量数据。
- 机制启用与标签事实发布是两条独立发布轴。

## 三、方案比较

### 方案一：所有类目共用一个混合队列

优点是实现最少；缺点是不同类目、机制版本和黄金集容易互相污染，单一大类目还会饿死低量类目。该方案不采用。

### 方案二：全局控制加类目独立泳道

全局层负责总预算、总并发、熔断和公平调度；类目泳道负责启用代次、组批、预算配额、黄金集、候选和回归。它复用现有常驻工作进程，又能做到完全隔离。该方案为冻结方案。

### 方案三：每个类目一套独立工作进程

隔离最强，但会复制调度、状态、恢复、预算和监控能力，运维成本高，也违背标签实验台统一底座原则。该方案暂不采用。

## 四、总体架构

### 4.1 全局控制层

保留现有全局自动化策略作为平台硬上限，负责：

- 全平台真实调用总开关；
- 全平台每日预算上限；
- 全局并发和公平调度；
- 租约、重试、熔断和恢复；
- 禁止自动发布的永久安全约束；
- 全局运行状态和审计。

全局开关不再直接决定某条历史案例是否可消费。

### 4.2 类目泳道策略

新增一等、版本化的类目泳道策略。建议以“类目 + 链路类型”为唯一键，至少冻结：

- 是否启用；
- 启用代次和启用时间；
- 允许的纠偏来源；
- 组批数量门槛；
- 最长等待时间和最低成批数量；
- 即时触发严重度；
- 类目每日预算配额；
- 冷却时间；
- 单次最大候选数；
- 目标错例、稳定对照、盲测保留三类回归样本集；
- 类目质量门槛；
- 操作人、修订号和审计时间。

所有活动类目都可以启用，但缺少调优模型、冻结机制、黄金集或预算时，只阻塞自身泳道。

### 4.3 案例资格快照

现有优化案例增加不可变资格快照，至少包含：

- 类目；
- 增量或存量链路；
- 启用代次；
- 冻结机制指纹；
- 来源任务或回归轮次；
- 纠偏节点、改前值、改后值；
- 结构化理由和证据；
- 人工结论修订；
- 路由建议；
- 是否属于历史审计案例；
- 是否满足自动消费条件。

机制指纹必须覆盖模型、调用甲、调用乙、维度合同、第三版规则、评分引擎和等级映射，不能只按单一提示词版本组批。

## 五、案例进入与自动组批

### 5.1 完整性门禁

只有最终人工纠偏且满足以下条件的案例才能自动消费：

- 人工身份和时间可追溯；
- 纠偏节点明确；
- 改前值和改后值完整；
- 纠偏理由非空；
- 需要证据的节点具有有效证据；
- 冻结机制身份完整；
- 类目和链路可确定；
- 不属于启用前历史积压。

缺失信息的案例进入“待补证据”，不能被人工总等级覆盖或系统猜测补齐。

### 5.2 组批键

案例只在以下字段完全一致时进入同一批次：

```text
类目
+ 增量/存量链路
+ 启用代次
+ 冻结机制指纹
+ 纠偏节点路由组合
```

这样可以防止不同调用链、不同规则版本或不同回归轮次互相污染。

### 5.3 触发规则

- 普通触发：达到类目配置的案例数量门槛。
- 高风险触发：配置为即时触发的严重问题无需等待满批。
- 低量类目触发：达到最长等待时间且满足最低成批数量时自动启动。
- 所有触发均先经过预算、黄金集、机制完整性和执行器就绪检查。
- 某泳道被阻塞时，调度器继续服务其他类目，不能造成全局饥饿。

## 六、机制归因与候选生成

### 6.1 路由规则

系统根据运营纠偏节点、理由和证据自动判断修改位置：

| 纠偏类型 | 主要候选位置 |
|---|---|
| 范围、内容事实、画质、媒介、硬伤识别错误 | 调用甲 |
| 美感维度、视觉证据、优缺点描述错误 | 调用乙 |
| 权重、扣分、封顶、豁免、阈值或等级映射错误 | 第三版规则 |
| 多节点共同导致 | 生成单个组合候选包，并记录内部依赖顺序 |

人工理由与证据是路由依据，模型不得只根据最终等级差异猜测原因。

### 6.2 候选约束

- 每次生成新的不可变版本，不覆盖现役或历史版本。
- 候选只允许修改当前类目和当前批次命中的能力节点。
- 候选必须附带修改前后差异、目标错误、预期收益、潜在副作用和回退对象。
- 缺少新信息时不得生成仅改名称或机械平移阈值的伪候选。
- 一次候选可包含调用甲、调用乙和第三版规则的组合修改，但必须分别记录贡献和风险。

## 七、自动回归与人工二审

### 7.1 三角色配对回归

每个候选必须冻结并完成：

1. 目标错例：验证本批纠偏问题是否修复；
2. 稳定对照：验证原本正确的能力没有退化；
3. 盲测保留：防止候选只记住当前纠偏样本。

增量和存量链路分别形成回归证据，不能互相替代。

### 7.2 技术失败与业务失败分离

- 超时、限流、解析失败、无效结构属于技术失败，可按策略重试。
- 准确率、召回率、覆盖率或业务护栏不达标属于业务失败，不自动重试为成功。
- 技术覆盖不足时不计算或不采用业务结论。
- 任何失败都保留原始任务、尝试次数、脱敏错误、模型与机制版本。

### 7.3 二审证据

人工二审页面必须一次展示：

- 纠偏案例聚类与代表样本；
- 候选修改前后差异；
- 调用甲、调用乙、第三版规则的路由理由；
- 目标错例、稳定对照和盲测保留指标；
- 技术覆盖率和技术失败；
- 质量收益、退化项和风险；
- 采用后的影响范围；
- 明确的“采用”与“拒绝”动作。

人工拒绝后保留证据，可继续积累新案例；不得删除失败候选。

## 八、灵感图专项机制迭代

灵感图继续输出五档，但以三条业务边界作为主要攻关面：

1. 推荐档与常规档边界：防止需要降权的第三档进入第一档/第二档推荐层。
2. 第三档与第四档边界：使常规档内部能够稳定分层降权。
3. 第五档与常规档边界：第五档漏判成本更高，优先提高召回并用豁免控制误杀。

### 8.1 指标门槛

- 推荐档按第一档和第二档合并计算，精确率和召回率均不低于 80%。
- 推荐档素材占比目标不超过 35%，运营目标约 30%。
- 第三档、第四档分别要求精确率和召回率均不低于 80%。
- 第五档精确率和召回率均不低于 80%，优化时召回优先。
- 第一档误升成本更高，第一档相关决策以精确率为主。
- 同时保留五档混淆矩阵、精确等级命中和相邻等级命中作为诊断证据。

### 8.2 机制结构

- 调用甲负责范围、内容事实、画质、媒介、硬伤和第五档过滤信号。
- 调用乙独立判断美感基础与推荐资格，不承担最终等级映射。
- 第三版规则只做可信信号组合、优先级、封顶、豁免和确定性定级。
- 第一档/第二档只在推荐素材内部细分。
- 非推荐、非过滤素材再区分第三档和第四档。
- 不再依赖全局平移阈值弥补缺失信号。

## 九、产品界面补全

### 9.1 全局自动化总览

展示全平台总预算、总并发、活动泳道、阻塞泳道、历史审计积压、运行中批次、待二审候选和最近失败。

### 9.2 类目泳道详情

每个类目分别展示增量/存量状态、启用代次、下一批门槛、候选生成状态、黄金集就绪度、预算和阻塞原因。

### 9.3 纠偏工作台

最终纠偏提交后直接展示“已进入自动分析”的追踪状态，不再提供“启动纠偏分析”作为正常流程按钮；管理员只保留失败重试和历史案例人工纳入入口。

### 9.4 候选二审

候选、回归、风险和采用决策收敛到同一证据区域，避免运营在多个页面之间寻找结果。

## 十、并发、幂等与恢复

- 同一人工纠偏修订只能生成一个资格快照。
- 同一组批键和案例集合只能生成一个自动化批次。
- 同一候选版本只能生成一组冻结回归任务。
- 重启后从已完成检查点继续，不重复调用模型或重复生成候选。
- 租约过期可恢复；仍在有效租约中的任务不得被第二个工作进程领取。
- 类目公平调度延续现有确定性轮转，增加泳道预算和最大连续占用限制。
- 候选采用、标签发布和存量重跑均保持独立幂等键。

## 十四、验收标准

### 14.1 自动化闭环

- 所有活动纠偏类目都有独立泳道。
- 新纠偏案例可自动进入候选二审，中间不要求人工点击。
- 类目、增量/存量、机制版本和启用代次不会混批。
- 历史约 2,286 条积压保持审计态，自动消费者读取数为零。
- 阻塞一个类目不会阻塞其他类目。
- 技术失败和业务失败可分别统计、重试和审计。
- 人工采用前没有机制指针变化，采用后没有自动存量重跑或标签发布。

### 14.2 灵感图

- 推荐档占比不超过 35%。
- 推荐档、第三档、第四档、第五档精确率和召回率分别达到冻结门槛。
- 第一档误升和第五档漏判分别按业务成本重点展示。
- 候选报告包含五档矩阵、三档兜底口径、技术覆盖和疑难案例。

### 14.3 工程与兼容

- 全部未发布包有分支、提交、文件、迁移、测试、依赖和部署状态台账。
- combined 合流保留主线和 3D/SU dry-run 两侧能力。
- 后端专项与全量测试通过。
- 前端合同、类型检查和生产构建通过。
- 真实浏览器完成全局总览、类目泳道、纠偏追踪和候选二审验收。
- 数据库完整性、外键、迁移幂等和旧数据隔离通过。

## 十五、权限、风险与回退

### 已授权

- 在独立工作树编写和提交设计、计划及后续经确认的本地实现。
- 使用测试替身、隔离数据库和本地浏览器进行验证。
- 与标签实验台任务协调迭代包台账和文件边界。

### 尚未授权

- 推送或合并 Codeup；
- 部署测试服或生产环境；
- 打开测试服全局自动化开关；
- 设置真实预算或启动真实调优模型调用；
- 自动采用候选、覆盖存量或发布标签事实；
- 删除、重写或清理旧分支和脏工作树。

### 主要风险

- 全局开关误吞历史积压；
- 不同类目或机制版本混批；
- 候选对当前纠偏样本过拟合；
- 单类目消耗全部预算或阻塞全局调度；
- 与未发布 3D/SU 包发生迁移和工作进程冲突；
- 把技术失败误算为业务误判。

### 回退

- 每个类目泳道可独立关闭，不改变其他类目。
- 自动化批次、候选和回归均为追加式记录，可停止消费者而不删除证据。
- 机制采用可以回退到上一现役版本；标签事实和存量结果不随机制回退自动改写。
- 合流使用独立分支，原主线和所有旧工作树保持不变。

### 立即停止条件

- 发现历史案例进入自动消费；
- 发现跨类目、跨链路或跨机制版本混批；
- 候选未经人工采用即改变现役指针；
- 迁移改写人工真值、历史评测或正式标签事实；
- combined 合流丢失主线或未发布包能力；
- 真实费用、外部写入或部署在未授权情况下被触发。

## 十六、当前非阻塞未决项

- 每个类目的具体组批数量、最长等待时间和预算配额由部署前配置冻结。
- 当前标签实验台会话的未提交文档包完整提交号仍待其收口回执。
- 测试服实际启用时间、真实预算和调优模型调用需后续单独授权。

这些未决项不影响规格、计划和本地实现，但会阻止真实启用与部署。
