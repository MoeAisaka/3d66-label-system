# TPENG 标签体系重构研发启动与 3D/SU 九月闭环设计

- 状态：设计已由 Owner 分段确认，等待书面规格复核
- 日期：2026-08-15
- 硬截止：2026-09-30
- 产品主体：TPENG 标签实验台（LabelLab）
- 首个真实切片：3D/SU 模型标签生产与消费闭环
- 关联决策：ADR-0042、ADR-0043、ADR-0045、ADR-0047

## 1. 结论先行

“标签体系重构”与“标签实验台”不再作为两条项目线。TPENG 标签实验台是新标签体系的事实产品，统一承载下游字段需求、素材接入、自动打标、美感评测、人工纠偏、AI 机制优化、双发布轴、正式事实、消费投影、对账与 Badcase 回流。

本方案不重写现有 LabelLab，也不先建设一个脱离业务的大平台。采用“现有底座演进 + 标准契约 + 3D/SU 真实纵切”的路径：在补齐平台通用边界的同时，于 2026-09-30 前使用真实 3D/SU 素材、真实模型和经审批的真实数据库链路跑通标签闭环。3D 搜索真实用户灰度是冲刺目标，不是九月必达条件。

日常接入、路由、打标、美感评测、风险分流、抽样、候选生成和回归由系统自动推进。人工保留三类介入：抽查纠偏、异常仲裁，以及两个彼此独立的最终门禁：

1. 机制发布门：决定新的模型、Prompt、V3、规则或脚本组合是否用于未来任务；
2. 标签事实发布门：决定候选事实是否成为下游可消费的正式 Canonical 事实。

机制启用不自动覆盖存量标签，也不自动发布标签事实。

## 2. 目标与成功定义

### 2.1 九月必达

在 2026-09-30 前完成以下真实链路：

```text
真实3D/SU素材（res_type=1/6）
→ 自动接入与类目路由
→ 语义打标 + 美感评测 + 治理处理
→ 风险分流与人工抽查纠偏
→ AI生成机制候选并自动回归
→ 人工批准机制
→ 人工批准标签事实
→ 正式事实投影至真实大维表/小表
→ 下游读取与确定性对账
→ Badcase回流标签实验台
```

必达闭环必须使用真实素材、真实模型和经审批的真实数据库读写链路。允许采用小批量金丝雀，不要求一次处理全部存量。

### 2.2 九月冲刺

在必达闭环之上，接入 3D 搜索真实用户灰度和效果指标，完成搜索 Badcase 回流。若搜索团队的接口、流量或排期未准备好，不影响标签中台闭环本身的九月验收，但必须保留明确的依赖、Owner 和后续日期。

### 2.3 长期目标

将 3D/SU 验证出的通用能力沉淀为全类目底座。灵感图、案例/效果图和后续类目只扩展字段适用性、输入合同、Prompt、模型、规则、门槛和专用视图，不复制模型管理、任务调度、纠偏、发布、投影和反馈能力。

## 3. 方案选择

本次比较了三条路径：

1. 统一底座演进 + 3D/SU 纵切：复用现有 LabelLab，边做真实闭环边沉淀通用模块；
2. 平台内核优先重构：先完成完整事件总线、工作流引擎、事实库和投影服务，再接业务；
3. 业务功能继续堆叠：围绕 3D/SU 直接补页面、接口和落表，不治理平台边界。

选择方案 1。它能在九月给出真实结果，同时避免方案 2 的价值延迟和方案 3 的类目复制。实施采用模块化单体演进，不以九月 DDL 为理由启动全面微服务拆分。

## 4. 总体架构

新标签体系采用“一套事实产品、双运行平面、七个能力域、三个横向治理中心、两个独立人工门”。

### 4.1 双运行平面

- 生产执行平面：真实接入、任务运行、模型调用、人工纠偏、事实发布、数据库投影和下游对账；
- 策略治理平面：字段合同、Schema、词表、模型、评测机制、自动化脚本、黄金集、AI 迭代和回归验证。

两个平面共享资产身份、人工真值、版本和审计底座，但权限、运行状态、资源和发布动作隔离。

### 4.2 七个能力域

1. 下游需求合同、Schema 与词表；
2. 素材接入、资产身份与版本；
3. 自动任务编排与运行调度；
4. 类目插件、自动打标与美感评测；
5. 人工抽检、纠偏、复核、仲裁与黄金数据；
6. Canonical 事实、双发布轴与存量重跑；
7. 消费投影、消费者对账、效果度量、Badcase 回流与证据审计。

### 4.3 三个横向治理中心

- 模型中心：主模型、调优模型、Benchmark 模型、协议、Token、价格、限额、思考开关/层级和类目绑定；
- 机制中心：Prompt A/B、V3 合同、规则、门槛、现役/候选/历史版本和自动回归；
- 脚本与工作流中心：输入输出合同、版本、依赖、超时、重试、并发、成本、Owner、日志和回退。

## 5. 事实主权与数据边界

### 5.1 Canonical 事实

- `semantic.*`：对象、空间、风格、材质、颜色、结构、软装、硬装、标题等语义字段；
- `quality.*`：美感等级、维度、技术质量、过滤判断、风险和证据；
- `governance.*`：来源、版权、状态、删除、审核、发布和治理信息。

模型原始输出先形成候选。人工确认值、来源、证据、字段合同、素材版本、模型、机制、脚本、审核和发布状态必须可追溯。美感评测是 `quality.*` 子任务，不是独立于标签生产之外的工具。

### 5.2 消费投影

统一大维表、搜索标签小表、质量治理小表、搜索索引、知识图谱和向量索引均是可重建消费投影，不是事实主库。投影只能读取正式发布事实，必须携带资产、标签、机制、模型和投影版本，并能按数量、缺失、版本和确定性哈希完成对账。

Query×素材相关性、排序权重、多路召回融合、在线实验参数和知识图谱内部关系属于下游策略，不进入素材 Canonical 事实。

## 6. 资产身份与版本

3D/SU 跨表不得只使用 `ll_id`。身份合同至少包含：

```text
source_system + res_type + ll_id
```

其中 `res_type=1` 表示 3D 模型，`res_type=6` 表示 SU 模型。`content_key` 由完成唯一性验证后的业务复合键确定性生成，`asset_version_id` 单独表示素材版本。

首个候选键为 `source_system + res_type + ll_id`。生产激活前必须执行只读唯一性探查；若仍有重复，再引入权威 `res_id`。不得凭经验临时拼接主键。素材更新、删除、乱序事件和重放均产生新版本或事件证据，不原地覆盖历史运行。

## 7. 核心业务对象

| 对象 | 职责 |
|---|---|
| `DemandContract` | 定义下游字段、粒度、空值语义、质量门槛、时效和 Owner |
| `Asset/AssetVersion` | 表达统一素材身份和不可变素材版本 |
| `CategoryProfile` | 声明类目适用字段、模型、机制、步骤、门槛和专用视图 |
| `WorkflowDefinition` | 编排自动步骤并引用不可变脚本版本 |
| `ProductionRun/StepAttempt` | 记录一次生产运行及逐步执行、重试和检查点 |
| `CandidateFact` | 模型、规则或脚本生成的候选字段，不允许下游消费 |
| `HumanTruth` | 人工确认值、原因、证据、审核人和修订 |
| `MechanismRevision` | Prompt、V3、规则、模型和脚本绑定及回归证据 |
| `PublishedFact/LabelRelease` | 经人工批准的正式 Canonical 标签事实 |
| `ProjectionManifest/FeedbackCase` | 投影输入输出、对账结果及下游 Badcase 回流 |

所有生产运行冻结素材版本、字段合同、类目 Profile、模型、Prompt、V3、规则、脚本和环境。历史运行不得读取后续的“最新版本”重算解释。

## 8. 3D/SU 生产状态流

```text
真实接入事件
→ 身份解析和幂等校验
→ 冻结素材版本、字段合同和类目Profile
→ 通用语义标签生成
→ 3D/SU专有标签生成
→ 美感调用A/B和V3评分
→ 词表映射与冲突检测
→ 治理检查
→ CandidateFact
→ 置信度、冲突和抽样风险分流
→ 人工抽查/纠偏/仲裁
→ HumanTruth
→ 正式事实候选
→ 人工事实发布门
→ PublishedFact
→ 大维表/小表投影
→ 下游读取与对账
→ FeedbackCase
```

AI 机制优化使用已确认纠偏样本自动聚类、查漏补缺、生成完整机制候选并执行回归。人工只在回归完成后启用或拒绝候选，不再手工配置分析过程。机制启用只影响未来任务；存量重跑和事实发布仍需独立动作。

## 9. 脚本注册与工作流编排

### 9.1 脚本版本合同

每个可执行步骤必须登记：名称、用途、Owner、适用类目、运行方式、制品哈希、输入输出 Schema、依赖字段、前置步骤、幂等键、超时、重试、并发、限流、模型成本、凭据引用、健康结果、历史运行和回退版本。

生命周期为：

```text
draft → validating → active → deprecated → retired
```

异常版本进入 `blocked`，阻止新任务使用但保留历史解释。

### 9.2 标准步骤类型

1. `connector`：素材或事件接入；
2. `identity`：资产身份与版本解析；
3. `transform`：清洗、格式转换和标准化；
4. `model_call`：语义打标、美感评测或专项识别；
5. `rule_eval`：V3、词表映射、治理和风险规则；
6. `human_task`：抽查、纠偏、复核或仲裁；
7. `release_gate`：机制或标签事实人工门；
8. `projection`：大维表、小表或索引投影；
9. `reconcile`：数量、版本和哈希对账；
10. `feedback`：下游效果和 Badcase 回流。

### 9.3 安全边界

管理员可以组合平台已经发布的步骤、配置允许开放的参数、调整条件路由并绑定类目、模型和机制版本，但不能通过页面上传并执行任意 Python、JavaScript、SQL 或 Shell。新增底层执行器仍需研发发布、安全验证和回归门禁。

## 10. 类目插件与快插快拔

`CategoryProfile` 是唯一类目扩展入口，负责声明：适用字段、输入素材形态、工作流模板、主模型/调优模型、Prompt A/B、V3 合同、词表映射、风险门槛、黄金集和专用编辑视图。

类目插件不得实现自己的队列、模型中心、纠偏系统、发布系统或投影系统。新增类目的标准过程为：

```text
注册字段适用性
→ 选择标准步骤
→ 补充必要的类目专有步骤
→ 绑定模型和机制
→ 配置黄金集与门槛
→ 回归
→ 人工启用
```

未知、未启用、合同不兼容或缺少执行器的 Profile 只能只读诊断，禁止创建候选或启动生产任务。

## 11. 并发、队列与资源治理

共享执行内核提供五类队列：

- `validation`：黄金集、挑战集和发布回归；
- `interactive`：人工触发的小批实验和复判；
- `production_batch`：正式增量及批量生产；
- `canary`：新旧版本金丝雀；
- `recovery`：补偿、重试和异常恢复。

各队列拥有独立配额，可受控借用空闲资源。模型供应商限流、Token 成本、类目优先级、重试退避、错误熔断和恢复限速由全局调度统一处理，避免单一类目或错误脚本占满资源。运行记录必须显示队列、配额、检查点、阻塞原因、下一次重试和责任人。

## 12. 前端信息架构与人工协作

### 12.1 七个一级工作域

1. 今日工作：待纠偏、待审批、异常和 SLA 风险；
2. 增量生产：新增素材自动接入、任务进度和发布；
3. 存量治理：素材包、回归、差异审核和存量重跑；
4. 人工工作台：抽查、纠偏、复核和争议仲裁；
5. 质量与策略：黄金集、指标、AI 迭代和机制回归；
6. 发布与消费：标签事实发布、投影、消费者和对账；
7. 平台治理：字段合同、类目、模型、机制、脚本、权限和审计。

增量与存量任务页面和上下文隔离，但共享执行内核和治理能力。

### 12.2 页面收束原则

一级页面只展示当前任务、当前步骤、成功/阻塞/异常状态、最少必要的质量证据、允许执行的动作和下一步责任。Prompt 全文、V3 JSON、模型参数、历史版本、完整矩阵、失败日志和高级配置进入二级抽屉、Dialog 或专用工作台。

### 12.3 待办决策箱

所有需要人工介入的事项进入统一待办中心，包括低置信纠偏、随机抽查、争议仲裁、机制候选批准、事实发布批准、存量重跑差异确认和投影回退审批。

每个待办必须直接说明：为什么需要处理、影响哪些素材和字段、系统已经完成什么、推荐动作及风险、处理后系统将自动完成什么。不得要求用户自行寻找配置页面或另建候选版本。

### 12.4 原位纠偏

人工在错误字段旁直接查看并修改“模型值 → 人工值”，选择结构化原因，可补充文字和图片证据，支持撤销、批量同类纠偏和保存后自动下一张。总分、等级和派生字段由服务端重算，人工不能改模型原始响应或直接填写派生结果。

纠偏结果自动进入黄金候选和 AI 分析输入。

### 12.5 双门决策卡

机制发布卡展示配置差异、基准/候选指标、受益和退化样本、影响范围、风险和回退版本。标签事实发布卡展示素材、字段、人工覆盖、字段质量、目标投影、消费者、对账方式和回退点。人工只批准或拒绝，不重新配置自动过程。

### 12.6 桌面端边界

正式工作台只考虑公司内网桌面浏览器，以 `1440×900` 为主设计宽度，保证 `1280×720` 可操作。不建设移动端审核和配置能力。

## 13. 全链路追溯

任一素材或 Badcase 必须能够正向和反向追溯：

```text
接入事件
→ 素材版本
→ 工作流与脚本版本
→ 模型和机制版本
→ 模型证据
→ 人工纠偏
→ 标签发布
→ 投影批次
→ 消费者版本
→ 下游反馈
```

从一个错误标签也必须能定位它影响的表、索引、消费者和回流工单。

## 14. KPI 与发布门槛

### 14.1 主要结果指标

1. 标签质量：按类目、字段、标签值和版本分别计算 Precision、Recall。首期默认门槛为 Precision ≥ 80%、Recall ≥ 70%；关键字段不得低于现役基线，P0/P1 高风险错误不得增加。字段可以配置更强门槛；降低默认门槛需 Owner 重新批准。
2. 闭环证据完整率：进入正式发布的试点素材 100% 可追溯到素材版本、合同、脚本、模型、机制、人工记录、发布和投影；缺少任一环节不得计为闭环成功。
3. 投影对账一致率：正式试点批次的版本、数量、主键和确定性哈希必须 100% 对账。

### 14.2 驱动指标

- 机器流水线有效完成率 ≥ 95%；
- 1000 个图片或等价模型处理单元的机器侧链路 ≤ 4 小时；
- 重复事件不产生重复事实或重复投影；
- 人工纠偏完成后自动进入 AI 分析和回归，不增加人工配置步骤；
- 人工介入率先建立真实基线，再设降本目标。

### 14.3 质量展示

字段指标必须展示对象粒度、分母、样本版本和排除项。美感评测继续保留 L1–L5 五档矩阵、各档 Precision/Recall、精确等级准确率、相邻等级准确率，以及推荐档 L1/L2、常规档 L3/L4、过滤档 L5 的聚合指标。聚合档位不能替代五档矩阵。

### 14.4 护栏

- 候选、实验结果和人工过程不得被下游消费；
- AI 不得自动启用机制或发布标签事实；
- 机制启用不得自动覆盖存量；
- 未完成审批、快照和回退门禁不得执行真实数据库 DML；
- 任何质量硬门槛不通过时，成本或速度改善不能替代质量验收。

## 17. 错误处理与恢复

以下情况关闭失败并进入异常中心：身份无法唯一确定、字段合同/Profile/模型/脚本版本缺失、重复事件 Payload 不一致、素材版本漂移、模型结构非法或越权、投影与 Canonical 版本不一致、消费者数量/版本/哈希对账失败。

恢复从安全检查点继续，不重新执行已经成功且具备幂等证据的步骤。禁止使用空标签、无版本的“最新配置”或人工补 SQL 伪装成功。

回退分为五层：

1. 代码版本回退；
2. 模型、机制、脚本和工作流现役指针回退；
3. 标签事实使用新的补偿 release，不删除历史；
4. 投影按稳定 release 重建；
5. 旧消费链路在新链路对账和切流完成前保留。
